# Инструкции для работы с проектом

Этот файл действует для всего репозитория. Общайся с пользователем на русском языке.
Перед изменениями читай затрагиваемый код и проверяй `git status --short`.
Сохраняй пользовательские изменения и ограничивай правки поставленной задачей.
Обновляй этот файл, когда меняются архитектура, команды или важные ограничения.

## Назначение и стек

Интернет-магазин с серверным HTML-интерфейсом: регистрация, профиль, каталог,
корзина, оформление и выдача заказов, история покупок и накопительные скидки.
Клиент покупает товары, оператор обслуживает пункт выдачи, администратор
управляет товарами, категориями и продавцами.

- Java 21, Maven; Spring Boot 3.4.2 (`pom.xml`).
- Spring MVC, Thymeleaf и `thymeleaf-extras-springsecurity6`.
- Spring Security: сессии, вход по форме, BCrypt.
- Spring Data JPA / Hibernate, MySQL, Liquibase.
- Lombok 1.18.36, MapStruct 1.6.3; процессоры аннотаций настроены в Maven.
- JUnit Jupiter, Mockito, AssertJ через `spring-boot-starter-test`.

Версии сверяй с `pom.xml`; не обновляй зависимости без связи с задачей.
Отдельной сборки frontend и менеджера JavaScript-пакетов в проекте нет.

## Правила изменений

- Контроллеры связывают формы, сервисы, модель представления и перенаправления.
  Бизнес-логику размещай в сервисах, запросы к БД — в репозиториях.
- При изменении сервиса согласуй интерфейс, реализацию и вызывающий код.
  Используй внедрение через конструктор, обычно `@RequiredArgsConstructor`
  и `private final` для зависимостей.
- Сохраняй транзакционные границы сервисов (`jakarta.transaction.Transactional`).
  Изменения managed-сущностей могут сохраняться через dirty checking;
  отсутствие отдельного `save()` само по себе не является ошибкой.
- MapStruct-конвертеры — Spring-компоненты. Редактируй объявления маппинга,
  а не сгенерированные реализации в `target/generated-sources/annotations/`.
  Для обновлений учитывай `NullValuePropertyMappingStrategy.IGNORE`.
- При изменении DTO проверяй маппинг, `@Valid`, имена полей форм и выражения
  Thymeleaf. При изменении контроллера проверяй имя шаблона, атрибуты модели,
  `th:action`, параметры запроса и redirect.
- Пользовательские сообщения, подписи статусов и интерфейс сейчас на русском.
  Сохраняй UTF-8 и стиль соседних файлов, избегай массового форматирования.

## Особенности предметной области

- Деньги представлены `BigDecimal`, количества — `Long`, процент скидки —
  `Integer`. Скидка округляется до двух знаков через `RoundingMode.HALF_UP`.
  Используй общую логику `Calculate`; не переходи на `double`/`float`.
- `Bag` имеет составной ключ пользователь + товар. Ключи позиций заказа и
  архива также составные; сверяй `@IdClass`, поля ключа и `PrimaryKeyUtil`.
- При оформлении корзина превращается в `UserOrder` и `UserOrderProduct`,
  сначала сохраняется `UserOrder` для получения ID, затем позиции заказа;
  рассчитывается сумма со скидкой, затем корзина очищается. Все шаги должны
  оставаться в общей транзакции обработки заказа.
- `productCount` — исходное количество, `actualProductCount` — фактическое
  количество к выдаче, `productPrice` — сохранённая цена позиции заказа.
  При положительном значении изменения добавление ограничено исходным
  количеством, уменьшение — нулём. Отрицательное входное значение может
  обойти эти ограничения; при изменении этого кода проверяй валидацию DTO.
- Статусы заказа: `CREATED`, `READY`, `CLOSED`, `REFUSED`. При закрытии или
  отказе создаются архивные сущности и удаляется активный заказ.
  Закрытие увеличивает сумму покупок пользователя и проверяет скидку;
  отказ сохраняет нулевую итоговую сумму.
- Архив содержит снимок данных: идентификатор и название товара, исходное
  и итоговое количество, цену, адрес пункта выдачи и суммы заказа.
  Историю нельзя пересчитывать по текущей цене товара. Сейчас итоговая сумма
  при закрытии использует текущую скидку пользователя — изменение этой
  политики является изменением поведения.
- Товары, категории и продавцы используют `ItemStatus.ACTIVE/DELETED`.
  Сохраняй мягкое удаление и фильтрацию активных записей.
- Внешняя пагинация начинается с 1; `PageRequest` получает `page - 1`,
  а `PageResponse` возвращает `page.getNumber() + 1`.
- Регистрация назначает `Role.CLIENT`, нулевую сумму покупок и скидку с ID `1`.
  Эта запись должна существовать в начальных данных.

## Доступ и конфигурация

- `adminPath=/administrator/`, `clientPath=/client/`, `operatorPath=/operator/`
  заданы в `application.properties`; часть redirect и шаблонов содержит
  буквальные пути. При изменении маршрутов проверяй оба варианта.
- Публичные маршруты: `/login`, `/registration`, `/saveNewUser`; остальные
  требуют аутентификации, разделы защищены соответствующими ролями.
- `User` реализует `UserDetails`; `getAuthorities()` формирует `ROLE_` + роль.
  Формы входа используют параметры `login` и `password`.
- Сохраняй CSRF-защиту и передачу токена в POST-формах. Для операций с ID
  проверяй принадлежность ресурса пользователю или пункту выдачи оператора;
  одна проверка роли по URL не подтверждает эту принадлежность.
- Просмотр заказа, смена статуса, изменение количества, закрытие и отказ
  используют общую проверку `UserOrderService.getUserOrderForOperator(id, operator)`.
  Контроллер передаёт текущего оператора через `@AuthenticationPrincipal`.
  При несовпадении пунктов выдачи или отсутствии назначенного пункта/ID
  выбрасывается `AccessDeniedException` до изменения данных.
  Для количества проверяется `userOrderId` из DTO, а не отдельный `id`
  перенаправления. Новые операции оператора должны использовать эту проверку;
  не возвращай вызываемые из контроллера перегрузки изменения заказа без
  параметра оператора. Внутренний `deleteUserOrder(id)` вызывается после
  проверки доступа в сервисе обработки заказа.
- Не выводи пароли, хэши, реквизиты подключения или целый объект `User`
  в логи и ответы: текущий `User.toString()` содержит `passwordHash`.
  Не копируй значения учётных данных из properties в документацию.

## База данных и миграции

Приложение подключается к MySQL `ShopSpringBoot` на порту `3306`;
хост берётся из `MYSQL_HOST`, по умолчанию `localhost`.
Учётные данные берутся из `DB_USERNAME` и `DB_PASSWORD` без значений
по умолчанию. Перед запуском приложения или Liquibase Maven plugin задай
их в окружении процесса; в IntelliJ IDEA — в Environment variables
соответствующей Run Configuration. Не добавляй реальные значения в код,
properties или общие конфигурации запуска. Сборка и unit-тесты не требуют БД.
Для локальных переопределений используй переменные Spring Boot
`SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`,
`SPRING_DATASOURCE_PASSWORD` без добавления секретов в Git.

`spring.jpa.hibernate.ddl-auto=none`: схема управляется Liquibase.
Главный файл — `src/main/resources/changelog/db.changelog-master.xml`,
Liquibase включён при старте приложения. Новые изменения схемы добавляй
отдельным changeset и подключай в master; не переписывай применённые changeset.
Согласуй имена таблиц/столбцов с JPA: используется
`PhysicalNamingStrategyStandardImpl`, в схеме есть имена в смешанном регистре.

Liquibase Maven plugin настроен отдельно в `pom.xml`, с properties в
`src/main/resources/liquibase.properties` и URL в конфигурации plugin.
Параметры username/password plugin получают `${env.DB_USERNAME}` и
`${env.DB_PASSWORD}` из окружения Maven; в liquibase.properties секретов нет.
Переопределения datasource приложения не гарантируют смену базы для plugin.
Перед запуском приложения или миграций проверь выбранную БД: master содержит
миграцию заполнения данных. Для проверки документации запуск БД не требуется.

## Сборка и проверка

Команды выполняются из корня. Предпочитай JDK 21 и Maven Wrapper;
первый запуск wrapper и загрузка отсутствующих зависимостей требуют сети.

```powershell
# Проверка среды
java -version
.\mvnw.cmd -version

# Все существующие тесты
.\mvnw.cmd test

# Один затронутый тестовый класс
.\mvnw.cmd "-Dtest=BagServiceImplTest" test

# Сборка JAR с тестами
.\mvnw.cmd package

# Запуск после настройки локальной MySQL
.\mvnw.cmd spring-boot:run
```

Для Linux/macOS используй `./mvnw`. Установленный `mvn` допустим как запасной
вариант, если wrapper недоступен; укажи это в результате проверки.

Существующие тесты преимущественно используют `MockitoExtension`, `@Mock`,
`@InjectMocks`, иногда `@Spy`; есть и тест конвертации архива без Mockito.
Они не поднимают Spring context и не требуют MySQL. Интеграционных тестов
контроллеров, security и репозиториев сейчас нет; часть тестовых методов пустая.
Успешный запуск таких методов не означает, что соответствующее поведение покрыто.

Для изменения логики добавляй или корректируй содержательные проверки результата
и ошибочных сценариев. Сначала запускай затронутые тесты, затем полный набор
перед завершением изменения Java-кода. Для шаблонов проверяй связку формы,
контроллера и DTO; при доступном приложении проверь затронутый сценарий в браузере.
Для правок только документации достаточно проверки содержимого и diff.
Сообщай точную команду, результат и причину, если проверка не выполнена.

Начальное наблюдение от 2026-10-13: `mvn -o test` остановился до выполнения
тестов, потому что в локальном кэше отсутствовал `org.apache.maven:maven-parent:pom:43`
для разрешения Maven Surefire 3.5.2. Это ограничение локального offline-запуска,
а не подтверждённая ошибка исходного кода. В PATH был JDK 24.0.2; настройки
проекта требуют Java 21. После подготовки среды состояние тестов нужно проверить.

Последующая проверка от 2026-10-13 на исправном JDK 21: сборка Java-кода
и 25 затронутых тестов доступа/обработки заказа прошли. Общая проверка доступа
покрыта в `UserOrderOperatorAccessTest`; отказ до изменения позиций и
архивирования проверяется в тестах соответствующих сервисов.
Полный `mvn test`: 95 тестов, одна существующая ошибка
`UserOrderServiceImplTest.showCreatedUserOrders` — `UnfinishedStubbingException`
из-за `when(...)` без `thenReturn(...)`. Не считай полный набор успешным,
пока этот отдельный дефект теста не исправлен.

После очистки отслеживаемых файлов и переноса учётных данных в окружение
`mvn -q -DskipTests package` на JDK 21 прошёл. Это проверка сборки без тестов;
подключение с реальными `DB_USERNAME`/`DB_PASSWORD` и миграции не запускались.

## Файлы, требующие осторожности

- `target/` — результат сборки; не редактируй и не добавляй его в Git.
- `logs/` и архивы `service.zip` / `service.rar` исключены из отслеживания
  и добавлены в `.gitignore`. Существующие локальные файлы сохраняются на диске.
  Рабочий исходный код находится в обычных `.java`-файлах; не добавляй архивы
  как резервные копии исходников в Git.
- `.env`, `.env.*` и локальные application/liquibase-конфигурации игнорируются;
  `.env.example` и `.env.sample` допускаются только без секретов.
  Spring Boot не загружает `.env` автоматически. Для этого проекта основной
  способ передачи учётных данных — переменные окружения.
- Удаление секретов из текущих файлов не очищает старую историю Git.
  Не переписывай историю без отдельного запроса; ранее опубликованные
  действующие пароли следует заменить.
- Не включай изменения runtime-логов, настроек IDE и локальной среды в задачу.
- Перед завершением проверь `git diff --check`, diff изменённых файлов
  и `git status --short`; в ответе кратко опиши изменения и проверку.
